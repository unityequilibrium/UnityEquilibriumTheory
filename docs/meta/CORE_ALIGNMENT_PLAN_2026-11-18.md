## เป้าหมาย

ตรวจ `core/` ทีละโฟลเดอร์ ทีละไฟล์ แล้วตัดสินแต่ละไฟล์ว่า:
- **ใช้ต่อ** ถ้าเป็นส่วนของสมการใหม่ (action แม่สามชั้น และ observation lane)
- **พัฒนาต่อ** ถ้าเป็นของเก่าที่เกี่ยวกับสมการใหม่ ให้ derive ใหม่จาก action แม่ เพิ่ม physics test และลงทะเบียน claim
- **เก็บ** ถ้าไม่เกี่ยวกับสมการใหม่ ติดป้าย `LEGACY_UNREVIEWED` ห้ามลบ

**รายการตรวจทุกไฟล์:**
1. ไฟล์นี้คำนวณอะไร และอยู่ชั้นไหน (1, 2, 3, observation หรือไม่เกี่ยว)
2. สัญลักษณ์ หน่วย และเครื่องหมายตรงกับ `THEORY_CARD.md` ไหม
3. มี physics test ตาม STANDARD §6 ไหม หรือมีแค่ test ตรวจ status/hash
4. ใครเรียกใช้: core, topic หรือ test
5. ถูกล็อก hash ไหม
6. ตัดสินป้าย A/B/C/D พร้อมเหตุผลหนึ่งบรรทัด และบอกว่าจะทำอะไรต่อ

**วิธีเก็บไฟล์ป้าย C (ต้องให้ผู้เขียนเลือก):**
- **ทาง 1 (แนะนำ):** ไฟล์ที่ไม่ได้ถูกล็อก hash และไม่มีใครเรียกใช้ ย้ายไป `core/08_history/legacy/` ส่วนไฟล์ที่ถูกล็อกหรือถูกเรียกใช้ คงไว้ที่เดิม ติดป้ายใน register และหัวไฟล์ README ของโฟลเดอร์ ไม่แตะเนื้อไฟล์
- **ทาง 2:** ย้ายทุกไฟล์ป้าย C และเพิ่ม locator map ให้ contract อ่านตำแหน่งใหม่ได้ ทางนี้ทำให้ core สะอาดกว่า แต่ต้องแก้ตัวอ่าน locator ซึ่งเป็นเครื่องมือที่ล็อก hash ไว้ จึงต้องเป็นรอบงานแยกที่ได้รับอนุมัติ

## ขั้น 3: พัฒนาต่อไฟล์ป้าย B

ไฟล์ป้าย B แต่ละกลุ่มกลายเป็นรอบวิจัยตามรูปแบบ wave (STANDARD §9):
- derive ใหม่จาก action แม่ หรือบันทึกว่า derive ไม่ได้ (FAILED)
- เพิ่ม physics test
- ลงทะเบียน claim ที่ L1
- ถ้าจะเทียบกับข้อมูลจริง ให้ร่าง Test Card ให้ผู้เขียนอนุมัติก่อน

ตัวอย่างที่คาดว่าจะเจอ: O(2) superfluid transport (W4), open-system heat flux (W5)

## กติกาที่ใช้ตลอดแผน

- ทำงานในโฟลเดอร์ `uet_harness` เดียว ไม่สร้างโฟลเดอร์ใหม่

- หนึ่งรอบต่อหนึ่ง commit พร้อมบันทึก ledger สั้น ๆ ภาษาธรรมดา และรัน CI 5 คำสั่งของ AGENTS.md §8 ก่อนส่ง

- push และเปิด PR เมื่อผู้เขียนสั่งเท่านั้น และหยุดถามเมื่อ ledger ที่ยังไม่ push ครบ 10 รายการ
